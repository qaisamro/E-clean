# تصميم قالب فاتورة نقطة البيع

> تحديث: نُشرت الميزة على Hostinger بموافقة صريحة بتاريخ 2026-11-08 بتوقيت Asia/Jerusalem. راجع [تقرير النشر والتحقق](POS_INVOICE_BUILDER_DEPLOYMENT.md). أقسام التطوير المحلي أدناه تصف التسليم السابق للنشر.

## حالة التسليم

تم التنفيذ محليًا بتاريخ 2026-11-08 بتوقيت Asia/Jerusalem. لم تُنشر هذه الميزة على Hostinger، ولم تُعدّل بيانات الإنتاج. لا توجد تعديلات Flutter أو Passport أو OTP أو الدفع أو قواعد احتساب الأسعار.

## نتيجة الفحص قبل التنفيذ

- المتجر مرتبط بصاحب الحساب عبر `vendors.user_id`، والطلب يحمل `orders.vendor_id`.
- `OrderVendorOwnership` يفحص تطابق ملكية المنتجات والخدمات مع متجر الطلب، و`StoreOrderAccess` يطبق صلاحيات القراءة والعزل. أعيد استخدامهما.
- توجد طلبات قديمة غير محسومة الملكية، وقد توجد منتجات مختلطة أو غير متطابقة مع `vendor_id`. لا يمكن توزيع الإجمالي وخصم الطلب ورسومه على متاجر متعددة بأمان دون بيانات إضافية؛ لذلك يمنع العارض الجديد نسبتها إلى متجر واحد. يحصل صاحب المحل على 404 وفق الحماية الحالية، والمسؤول على 409 مع رسالة تفسيرية. الفاتورة السابقة لم تُحذف.
- إعدادات المتجر الحالية محفوظة في `vendors` ولا تتضمن إعدادات قالب فاتورة مستقل. أضيف جدول واحد مخصص بدل تغيير بيانات المتجر الأصلية أو الإعدادات العامة للفواتير.
- القيم المالية التاريخية الموثوقة هي حقول الطلب `amount`, `discount`, `delivery_charge`, `total_amount` وسعر الصنف المحفوظ في `order_products.price`. قيمة الصفر محفوظة كما هي؛ عند غياب سعر الصنف لا يُستعمل سعر الكتالوج الحالي.
- توجد نسبة ضريبة عامة، لكن لا يوجد مبلغ ضريبة مستقل محفوظ على الطلب، ولا علاقة محفوظة للكاشير، ولا خصم تاريخي مستقل لكل صنف. تُخفى هذه التفاصيل عند غياب مصدرها، ولا تُحسب نسبة جديدة من إعدادات اليوم.
- الفاتورة السابقة تستعمل رقم الطلب؛ لا يوجد تسلسل مستقل للفواتير في نموذج الطلب الحالي. رقم الفاتورة في القالب الجديد يستخدم رقم الطلب أيضًا، ولا ينشئ قيدًا محاسبيًا أو ترقيمًا جديدًا.

## الاستخدام والمسارات

يجد صاحب المحل «تصميم قالب الفاتورة» ضمن إدارة نقطة البيع.

| الطريقة | المسار | الغرض |
| --- | --- | --- |
| GET | `/vendor/invoice-template` | محرر القالب الخاص بصاحب المحل الحالي |
| POST | `/vendor/invoice-template` | حفظ JSON الإعدادات وشعار اختياري |
| DELETE | `/vendor/invoice-template` | استعادة الافتراضي وحذف الشعار المخصص |
| GET | `/vendor/invoice-template/preview?order={id}` | معاينة طلب حقيقي من متجره؛ بدون رقم تظهر حالة فارغة صريحة |
| GET | `/orders/{id}/pos-invoice?copy=normal` | طباعة عادية |
| GET | `/orders/{id}/pos-invoice?copy=customer` | نسخة الزبون واسمه الحقيقي |
| GET | `/orders/{id}/pos-invoice?copy=store` | نسخة المحل واسمه الحقيقي |

جميع المسارات ضمن مصادقة الويب الحالية. محرر المتجر لا يقبل اختيار متجر آخر. الطباعة الجديدة لصاحب المحل تشترط صلاحية `order.show` ثم فحص ملكية الطلب؛ يستطيع root وadmin طباعة الطلبات المسموح بها باستخدام قالب متجر الطلب. العملاء والسائقون لا يستطيعون استعمال المحرر أو الطباعة الجديدة. لا يوجد API عام للقالب أو شعار خاص قابل للتحميل دون مصادقة.

تحتوي تفاصيل كل طلب على الأزرار الثلاثة. زر طباعة الفاتورة بعد بيع POS يستخدم العارض الجديد للحسابات المصرح لها، مع بقاء المسار السابق كبديل للأدوار الأخرى. بقيت الفاتورة السابقة والطباعة الأصلية للملصقات متاحتين.

## المحرر والمعاينة

- قالب JSON واحد لكل متجر، مع افتراضي جاهز عند عدم الحفظ. الخيارات تشمل المقاس واللغة والاتجاه والخط والحجم والألوان والحدود والمسافات والمحاذاة.
- معلومات المتجر المعروضة يمكن تخصيصها للقالب فقط، دون تغيير سجل المتجر. الحقول الفارغة لاسم المحل والعنوان والهاتف والبريد تعود إلى معلومات Vendor الحقيقية.
- الشعار قابل للتغيير والإخفاء وتعديل الحجم والمحاذاة. يُقبل PNG/JPEG/WebP حتى 1MB و2400×2400 فقط. SVG غير مقبول. الحفظ في قرص `local` الخاص ضمن مجلد منفصل لكل متجر؛ يُضمن في الاستجابة المصادق عليها بصورة data URI. الشعار القديم يُحذف بعد نجاح المعاملة. الاستعادة تحذف الشعار المخصص وتعود إلى شعار المتجر الأصلي إن وجد.
- الحقول الاختيارية قابلة للإظهار والإخفاء؛ النصوص العلوية والسفلية والعنوان والشكر والملاحظات قابلة للتعديل. ترتيب الأقسام يتم بأسهم متاحة بلوحة المفاتيح أيضًا.
- المعاينة تختار من أحدث 30 طلبًا سليم الملكية للمتجر. طباعة أي طلب قديم صالح متاحة من صفحة تفاصيله.
- عارض JavaScript واحد وملف CSS واحد يستخدمهما iframe المعاينة ووثائق الطباعة الثلاث. تغييرات النص واللون والمقاس والشعار والترتيب تنعكس عبر `postMessage` دون إعادة تحميل المستند. يتم التحقق من أصل الرسالة ومصدرها. تغيير الطلب وحده يجلب بيانات طلب جديد.
- النسخ الثلاث لها الإعدادات والمبالغ والمنتجات نفسها. يضاف فقط عنوان النسخة وهوية العميل أو المتجر الفعلية في الأعلى؛ الطباعة العادية لا تحمل عنوان نسخة خاصًا.
- خيار الباركود المحلي Code 39 يرمّز رقم الطلب الداخلي الحقيقي. لا يرمز هاتف العميل أو رمز المتابعة، ولا يستخدم خدمة خارجية. بيانات الترميز الرقمية راجعت مقابل [مرجع Code 39 في JsBarcode](https://github.com/lindell/JsBarcode/blob/master/src/barcodes/CODE39/index.js)؛ لا توجد حزمة أو خدمة جديدة مطلوبة.
- لا توجد أسعار أو إجماليات أو أرقام طلبات قابلة للتحرير ضمن schema الإعدادات. تُرفض مفاتيح مالية دخيلة وHTML وزوايا الوسوم وقيم CSS غير المسموحة. عرض النصوص يتم بـ`textContent` وتضمين JSON بواسطة `Js::from`.
- حفظ القالب واستعادته يستعملان Transaction وقفل صف المتجر. يوجد قيد فريد على `vendor_id` لمنع تكرار القالب عند الطلبات المتزامنة.

## الحدود المقصودة والبيانات القديمة

- مجموع الصنف هو الكمية × سعر الوحدة المحفوظ في pivot، دون إعادة بناء إجمالي الطلب أو تعديل أي قيمة. إذا لم يُحفظ السعر التاريخي يظهر «غير متاح». الإجمالي النهائي دائمًا من الطلب.
- الإضافات القديمة لا تحفظ سعرًا تاريخيًا في علاقة الطلب؛ تعرض أسماؤها مع توضيح غياب السعر التاريخي، دون استخدام أسعارها الحالية.
- ضريبة الطلب والكاشير وخصم الصنف لا تظهر ما لم تتوفر بيانات تاريخية موثوقة. لا تُضاف أعمدة مالية جديدة لاستكمالها.
- الخطوط محلية من الخطوط المتاحة في النظام، ولا توجد خدمة خرائط أو رسوم أو دفع أو خط مدفوع.
- JavaScript مطلوب للعارض الجديد. المسار القديم للطباعة لم يُستبدل أو يُحذف.

## الطباعة

- A4 يعرض جدولًا؛ 80mm و58mm يعرضان أسماء المنتجات وأسطر الكمية والأسعار بمرونة لتجنب ضغط الأعمدة.
- لا توجد تذييلات ثابتة أو ارتفاع ثابت يقص المحتوى. الأسماء الطويلة تلتف. رأس الجدول يتكرر عند الطباعة متعددة الصفحات.
- المقاس الحراري يجب اختياره أيضًا في تعريف الطابعة/نافذة الطباعة؛ CSS لا يستطيع ضمان اختيار درج الورق أو التحكم بقاطع الورق. استخدم مقياس 100% وهوامش مناسبة وأوقف رؤوس وتذييلات المتصفح.
- نسخة PDF في فحوص المتصفح استعملت طول ورق حراري 300mm للاختبار؛ الطول الفعلي وقص اللفة يعتمدان على التعريف والطابعة.
- الطباعة الأحادية قد تتجاهل الألوان، والخطوط تختلف قليلًا بين أنظمة التشغيل. تمت مراجعة صور وملفات PDF محليًا؛ لم تُجر تجربة على طابعة حرارية فعلية.

لتكرار الفحص في PowerShell من مجلد Web_Admin:

```powershell
$env:INVOICE_BROWSER_ARTIFACTS = Join-Path (Get-Location) 'storage/framework/testing/invoice-browser'
php vendor/phpunit/phpunit/phpunit --filter VendorInvoiceTemplateTest
node tests/Browser/invoice-builder.cjs
php vendor/phpunit/phpunit/phpunit
```

فحص المتصفح يستخدم Playwright المرفق ببيئة Codex وChrome المحلي. يمكن تحديد `CODEX_NODE_MODULES` و`CHROME_PATH` في بيئة أخرى. هذه أدوات فحص فقط ولا تدخل اعتمادات الإنتاج.

## Migration وخطة نشر لاحقة

يلزم Migration واحد، طُبق على MySQL المحلي فقط. لم يُشغّل أي Migration آخر معلق. لا يوجد backfill أو تغيير جماعي لبيانات المتاجر أو الطلبات. يحتاج الإنتاج موافقة منفصلة قبل أي تنفيذ.

بعد الموافقة: تُقارن الملفات الحالية، وتؤخذ نسخة احتياطية للملفات وقاعدة البيانات، ثم ترفع ملفات الميزة وحدها. تُشغّل الهجرة المحددة فقط بعد مراجعتها، وليس جميع الهجرات المحلية المعلقة:

```sh
php artisan migrate --path=database/migrations/2026_11_08_100000_create_vendor_invoice_templates_table.php --force
php artisan view:clear
php artisan view:cache
```

لا حاجة لتشغيل DatabaseSeeder أو إعادة تهيئة Passport أو تغيير أدوار الإنتاج. يجب اختبار الحساب المالك والمسؤول ومنع الحساب الآخر ومراجعة السجل. للرجوع تُستعاد الملفات؛ لا يُحذف جدول القوالب إلا بعد حفظ إعداداته وشعاراته إذا استُخدم فعليًا.
