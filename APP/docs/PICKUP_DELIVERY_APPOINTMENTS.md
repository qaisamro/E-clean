# حجز مواعيد الاستلام والتوصيل — تنفيذ محلي

التاريخ: 2026-11-09. لم يتم الاتصال بالإنتاج أو نشر ملفات أو تعديل قاعدة بيانات الإنتاج في هذه المهمة.

## المنفذ

- صفحة Vendor مستقلة لإدارة فترات الاستلام والتوصيل الأسبوعية، سعة كل فترة، مدة التجهيز بالساعات أو الأيام أو الدقائق، وأفق الحجز من يوم إلى 60 يوماً.
- كل صف فترة حجز واحدة لها بداية ونهاية وسعة. يمكن إضافة عدة فترات في اليوم. يُرفض تداخل فترات النوع نفسه، وتبقى فترات الاستلام والتوصيل مستقلة.
- إجازات يوم كامل أو إغلاق جزئي، للاستلام أو التوصيل أو كليهما. الإغلاق الجزئي المتداخل يجعل الفترة كاملة غير متاحة للحجوزات الجديدة.
- بطاقات أيام وأوقات داخل Checkout، حالات تحميل وفشل اتصال وعدم توفر، فترات غير متاحة مع السبب، اقتراح أول توصيل صالح، اختيار بديل، وملخص الحجز.
- مدة التجهيز تبدأ **من نهاية فترة الاستلام**، وتُحسب كزمن فعلي بالدقائق عبر UTC. اليوم في محرر المدة يعادل 24 ساعة.
- المواعيد المحلية بتوقيت `Asia/Hebron`، مع حفظ نسخة الحجز في UTC. تُستبعد بدايات ونهايات الفترات التي تقع في ساعة غير موجودة أو ملتبسة عند انتقال التوقيت الصيفي. نسخة بيانات IANA في PHP المحلي: `2025.2`.
- صلاحية الفترة وسعتها تُفحصان مجدداً عند تأكيد الطلب؛ عرض التوفر لا يحجز الفترة مؤقتاً.
- قفل صف Vendor ثابت داخل Transaction، مع قراءة مقفلة للحجوزات والإعدادات لمنع الاعتماد على snapshot قديم في InnoDB REPEATABLE READ. يستخدم تعديل الجدول وإعادة الجدولة القفل نفسه. حفظ الطلب والمنتجات ونسخة الموعد عملية واحدة.
- الحجوزات السابقة، بما فيها الطلبات القديمة دون سجل موعد جديد، تشغل الطاقة الاستيعابية. يحتفظ سجل الموعد بحدود الفترة الأصلية حتى بعد تغيير الجدول. الطلب الملغى يحرر سعته.
- عدم تغيير الأسعار والخصومات ورسوم التوصيل وعنوان الطلب. لم يتغير نظام المدن أو السلة أو Checkout المالي أو Passport أو OTP.
- الطلبات المختلطة تظل ممنوعة وفق آلية `OrderVendorOwnership` الموجودة؛ لا نفترض ملكية المتجر من قيمة يرسلها العميل وحدها.
- عرض التوفر يستخدم قراءة مجمعة للحجوزات، بدلاً من استعلام SQL لكل بطاقة موعد.

## طريقة الاستخدام

### صاحب المتجر

1. افتح «إدارة مواعيد الاستلام والتوصيل» من قائمة صاحب المحل، أو `/vendor/appointments`.
2. أضف فترات الاستلام لكل يوم، ثم فترات التوصيل بشكل مستقل، وحدد عدد الطلبات لكل فترة.
3. حدد مدة التجهيز وأفق إتاحة الحجز. أضف الإجازات أو الإغلاقات عند الحاجة.
4. بعد تحديث تطبيق الزبائن واختبار توافقه، فعّل الجدول واحفظه. يكون النظام المخصص معطلاً افتراضياً للمتاجر غير المهيأة.
5. تعديل الجدول لا يغيّر أي طلب قائم. يعرض القسم أسفل الصفحة آخر 100 طلب قادم غير ملغى أو مسلّم.
6. لإعادة جدولة طلب Pending أو Order confirmed فقط: اتفق مع العميل، أدخل فترتين صحيحتين من الجدول، دوّن السبب وأكد حصول موافقة العميل. تُفحص السعة ومدة التجهيز مجدداً. يُحفظ سجل التدقيق وهوية المنفذ والموعد السابق. الطلبات التي بدأ تنفيذها لا تُعاد جدولتها بهذا المسار.

تأكيد موافقة العميل هنا توثيق من صاحب المتجر، وليس توقيعاً أو موافقة إلكترونية من حساب العميل. لا تُرسل رسالة خارجية تلقائياً.

### الزبون

1. افتح Checkout لسلة المتجر المحدد واختر يوم وفترة الاستلام.
2. تظهر أول فترة توصيل متاحة بعد نهاية الاستلام ومدة التجهيز تلقائياً؛ يمكن تغيير اليوم والفترة.
3. راجع ملخص الموعدين، واختر عنوان التوصيل وطريقة الدفع الحالية ثم أكد الطلب.
4. إذا امتلأت الفترة قبل التأكيد، يرفض الخادم الحجز؛ حدّث التوفر واختر فترة أخرى. لا تُنشأ حجوزات جزئية عند رفض أحد الموعدين.
5. تغيير متجر Checkout يمسح اختيارات مواعيد المتجر السابق. فشل تحديث التوفر يمسح الموعدين حتى لا يُستخدم اختيار قديم غير متحقق منه.

## API والمسارات

### إضافات

| المسار | الاستخدام |
|---|---|
| `GET /api/vendors/{vendor}/appointments` | توفر متجر نشط، دون بيانات العملاء |
| `GET /vendor/appointments` | إدارة جدول المتجر المسجل دخوله |
| `POST /vendor/appointments` | حفظ الإعدادات، Web auth وCSRF وملكية المتجر |
| `POST /vendor/appointments/orders/{order}` | إعادة جدولة طلب مملوك للمتجر مع سبب وموافقة موثقة |

استعلام التوفر يقبل `date=YYYY-MM-DD` اختيارياً؛ افتراضياً يبدأ من يوم فلسطين الحالي. بعد اختيار الاستلام أرسل `pick_date` و`pick_hour=HH:mm` لإرجاع خيارات التوصيل المقيدة بالتجهيز.

```http
GET /api/vendors/6/appointments
GET /api/vendors/6/appointments?pick_date=2026-11-11&pick_hour=09:00
```

مثال بنية استجابة توضيحي فقط، وليس بيانات متجر إنتاج:

```json
{
  "message": "Store appointments",
  "data": {
    "enabled": true,
    "vendor_id": 6,
    "timezone": "Asia/Hebron",
    "processing_minutes": 120,
    "days": [{
      "date": "2026-11-11",
      "pickup": [{
        "date": "2026-11-11",
        "hour": "09:00",
        "title": "09:00 - 11:00",
        "starts_at": "2026-11-11T09:00:00+02:00",
        "ends_at": "2026-11-11T11:00:00+02:00",
        "is_booked": false,
        "reason": null,
        "remaining": 2
      }],
      "delivery": []
    }]
  }
}
```

### مسارات موجودة محفوظة

- `POST /api/orders`: الحقول الحالية نفسها `pick_date`, `pick_hour`, `delivery_date`, `delivery_hour`, `products`, `address_id`, `payment_type` و`vendor_id` الاختياري. لا يُطلب slot ID أو حقل جديد.
- `GET /api/pick-schedules/{date}` و`GET /api/delivery-schedules/{date}`: نفس الاستجابة القديمة دون `vendor_id`. إضافة `vendor_id` اختيارياً تدعم جدول المتجر؛ مسار التوصيل المخصص يحتاج أيضاً `pick_date` و`pick_hour` لإظهار الخيارات الصالحة بعد التجهيز.
- `pickupat` و`dlvryat` اسما ترجمة في Flutter، وليسا أعمدة جديدة. بقيا كما هما.
- استجابة الطلب تحتفظ بحقوله. الطلبات ذات الحجز الجديد تعرض الفترة الفعلية الصحيحة في نص `pick_hour` و`delivery_hour`، بدلاً من تحويلها إلى الفترات القديمة الثابتة ذات الساعتين. الطلبات القديمة دون سجل موعد تحتفظ بتنسيقها السابق.

### حد توافق مهم قبل التفعيل

النسخ المنشورة القديمة تجلب الجدول العام دون رقم متجر. لذلك لا يمكنها معرفة جدول مخصص عشوائي لمتجر بعينه دون تحديث التطبيق. لم نغيّر استجابة المسار العام كي لا نخلط جداول المتاجر أو نغيّر سلوك المتاجر القديمة.

للمتجر غير المفعّل: يستمر مسار الإضافة والجدول العام كما كان. للمتجر المفعّل: تُقبل الحقول القديمة، بما فيها بداية المدى `9-10` إن طابقت بداية فترة متاحة، ولكن **تُرفض المواعيد غير المطابقة للجدول أو مدة التجهيز أو السعة**. لا يوجد تجاوز للحماية لصالح تطبيق قديم.

بالتالي النشر الآمن هو Backend مع الجداول المخصصة معطلة، ثم Flutter، ثم تفعيل المتاجر تدريجياً. لا ندّعي دعماً كاملاً لاختيار الفترات المخصصة من تطبيق قديم لا يرسل هوية المتجر عند جلبها. هذه نقطة يجب حسمها قبل التفعيل على الإنتاج؛ تظهر أيضاً لصاحب المتجر في صفحة الإدارة.
