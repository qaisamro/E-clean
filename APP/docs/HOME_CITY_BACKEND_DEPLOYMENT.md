## نتائج الاختبارات على الإنتاج

**نجح 41 فحص API عام و18 فحص مطابقة إضافيًا مع قاعدة البيانات.**

| التحقق | النتيجة |
|---|---|
| `GET /api/cities` | HTTP 200، قائمة معرّفات مدن فريدة |
| `POST /api/cities/resolve` | HTTP 200، مطابقة دورا والخليل وبيت لحم ورام الله لنقاط مرجعية داخل حدودها |
| موقع خارج الحدود المعتمدة | HTTP 200 مع `city: null` |
| دقة GPS غير كافية، 200 متر | HTTP 200 مع `city: null` |
| خط عرض غير صالح | HTTP 422 |
| فلاتر المدن في vendors/services/products/offers/promotions/banners/wide | HTTP 200 للمدن المعتمدة |
| `city_id=invalid` في الواجهات الست | HTTP 422، لا رجوع إلى جميع المدن |
| واجهات التطبيق القديم دون `city_id` | الاستجابات مطابقة لما قبل النشر، مع إضافة `city/city_id` فقط إلى عناصر قائمة المتاجر |
| `/api/master` | مطابق لما قبل النشر، بما فيه إعدادات التشغيل والرسوم |
| `/api/addresses` و`/api/orders` دون مصادقة | استمر HTTP 401 كما كان، دون تخفيف المصادقة |

شملت مقارنة الاستجابات القديمة: المتاجر والخدمات والمنتجات والعروض وpromotions والبنرات العريضة وmaster والعناوين والطلبات. احتُفظ بحقول المتاجر العشرة السابقة وبالترقيم، وأسعار المنتجات واستجابات الكتالوج غير المفلترة بقيت مطابقة.

في مطابقة الفلاتر المستقلة مع بيانات قاعدة الإنتاج:

- دورا: متجر نشط واحد مرتبط بها، وخدمتان ومنتجان وعرضان، دون promotions أو بنرات عريضة مرتبطة بها.
- الخليل وبيت لحم: النتائج فارغة وفق ارتباطات المدن الحالية في الإنتاج؛ لم تُخترع ارتباطات أو إحداثيات لملئها.
- المتجر الذي لا يحمل مدينة بقي كما هو، ويظل متاحًا في القائمة القديمة غير المفلترة، ولا يُنسب تلقائيًا إلى مدينة.

فحص واجهة الإحداثيات على الإنتاج استخدم نقاطًا مرجعية جغرافية، وليس تجربة GPS جديدة للهاتف على الإنتاج. تجربة الهاتف الحقيقية الناجحة في دورا مع Backend المحلي موثقة في `HOME_CITY_REPAIR_REPORT.md`.

## ما حدث أثناء التنفيذ والتراجع

1. توقف التحضير أولًا بسبب اختلاف اتصال عميل mysqldump عن Laravel. لم تُفعّل ملفات حينها. أُصلح إعداد عميل النسخ الاحتياطي باستخدام UNIX socket نفسه الذي يستخدمه Laravel، دون تغيير اتصال التطبيق أو صلاحيات قاعدة البيانات.
2. نجحت اختبارات API العامة في المحاولة الأولى للتفعيل، لكن أداة التحقق الإضافية عبر CLI فشلت لأن تهيئة Laravel لم تربط Request بعد. طُبق **التراجع التلقائي فعليًا**: استُعيدت الملفات الأصلية وأُبطل كاشها، ولم تُستعد قاعدة البيانات لأن النشر لم يكتب فيها.
3. أُصلحت أداة التحقق فقط واختُبرت محليًا، ثم أُخذت نسخة احتياطية جديدة كاملة. نجح التفعيل النهائي وكل فحوص API والمطابقة وسلامة البيانات والسجلات.

الأدوات السابقة كانت تشغيلية مؤقتة خارج شجرة التطبيق وحُذفت من `/tmp` بعد الانتهاء. لم تُنشر ملفات PHPUnit أو Flutter أو بيانات الاختبار ضمن التطبيق.

قبل إصدار Flutter المعتمد على المدن، يمكن استعادة ملفات النسخة النهائية بالأمر التالي عبر SSH:

```sh

```

الأداة تتحقق من بصمات الملفات لتجنب الكتابة فوق تحديثات متزامنة، وتستعيد الملفات القائمة وتحذف الملفات الجديدة المدرجة فقط، ثم تحدث كاش الإعدادات والمسارات. بعدها يجب إبطال OPcache للملفات نفسها من Web SAPI بأداة مؤقتة محمية أو وسيلة الاستضافة المتاحة، وإعادة مقارنة الواجهات القديمة وفحص السجلات. إبطال OPcache من CLI وحده غير كافٍ.

**لا تُستورد `database.sql` في تراجع كود فقط**؛ ذلك قد يفقد طلبات حقيقية أُنشئت لاحقًا. SQL نسخة للتعافي من كوارث البيانات بخطة منفصلة عند الحاجة. بعد إصدار Flutter الجديد لا يُحذف عقد API للمدن الذي يعتمد عليه دون خطة توافق للعميل.
